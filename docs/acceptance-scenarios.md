# Проверка основных пользовательских сценариев

**Проект:** CRM-Агентство · **Основание:** ТЗ ред. 2.0, п. 6.2 · **Дата проверки:** 17.11.2026

Основная задача системы (ТЗ п. 2): обращения из разных каналов попадают в единую ленту, по ним автоматически заводятся клиент и лид, а дальше сделка проходит путь до оплаты и выполненного проекта — с задачами для дизайнера, счетом, контролем руководителя и кабинетом клиента. Семь приемочных сценариев ТЗ вместе покрывают этот путь целиком:

```
обращение (Telegram / сайт) → клиент и лид → «Входящие» → ответ и работа со сделкой
  → задача дизайнеру → макет в сделке → счет в PDF → оплата → проект и этапы
  → клиент видит этап в кабинете → руководитель видит отчеты и KPI
```

Каждый сценарий описан по критериям проверки: исходные условия, шаги, ожидаемый результат, независимая проверка (не по сообщению об успехе, а по данным в БД), существенные ограничения и воспроизводимость. Все сценарии дополнительно закреплены автотестами — их прогон воспроизводит сценарий на чистой базе (`cd backend && npm test`, 85 тестов).

## Общие исходные условия

```bash
docker compose up --build        # http://localhost:8080
```

- Система запущена одной командой, при первом старте применены миграции и создан демо-набор данных (сделки на всех стадиях, задачи, счета, проекты, отказы, расходы).
- Демо-учетные записи: `manager`, `manager2`, `head`, `designer`, `marketer`, `director`, `admin`, клиент `client`; пароль `demo12345`.
- Для сценариев 1–2 с Telegram в `.env` задан токен тестового бота и `TELEGRAM_POLLING=true` (см. README). Без токена сценарий 1 проверяется через форму сайта — путь приема тот же.
- Независимая проверка выполняется SQL-запросами к базе:

  ```bash
  docker compose exec db psql -U crm -d crm -c "<запрос>"
  ```

## Сценарий 1. Обращение появляется во «Входящих», создаются клиент и лид

**Требования:** FR-LEAD-01, 03, 04 · **Автотест:** `test/leads.test.js`

**Исходные условия:** клиента с таким Telegram-аккаунтом (или телефоном) в базе нет; менеджер `manager` открыл «Входящие».

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Написать тестовому боту в Telegram (или отправить заявку на странице «Форма сайта» с UTM-метками) | — |
| 2 | Смотреть ленту «Входящие» | Не позже чем через 10 с (опрос раз в 5 с) обращение появляется вверху, выделено как непрочитанное, с каналом и кампанией из UTM |
| 3 | Открыть обращение | Видны текст, канал, стадия «Новый»; ссылка на созданную карточку клиента |

**Независимая проверка:**

```sql
SELECT c.name, cc.channel, cc.external_id, d.stage, d.utm_campaign
  FROM clients c JOIN deals d ON d.client_id = c.id
  LEFT JOIN client_contacts cc ON cc.client_id = c.id
 ORDER BY d.id DESC LIMIT 1;
```

Появились одна строка клиента, контакт канала и сделка на стадии `new`.

**Ограничения:** повторная доставка того же сообщения (повтор вебхука, повторная отправка формы) не создает дубль — уникальный индекс `messages(channel, external_id)`; второе сообщение того же клиента попадает в его открытую сделку, а не в новую. Неверные данные формы отклоняются с понятным сообщением, ничего не сохраняется.

**Воспроизводимость:** новое обращение от другого клиента создает новые клиента и лид; повторное — дописывается в существующую сделку.

## Сценарий 2. Менеджер отвечает клиенту, клиент получает ответ в Telegram

**Требования:** FR-LEAD-06 · **Автотест:** `test/leads.test.js` (Telegram Bot API подменяется)

**Исходные условия:** задан токен бота; есть обращение из Telegram (сценарий 1).

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Во «Входящих» открыть обращение, ввести ответ, «Отправить» | Сообщение появляется в переписке справа, менеджер становится ответственным |
| 2 | Проверить Telegram клиента | Ответ пришел от бота |

**Независимая проверка:**

```sql
SELECT direction, body, external_id FROM messages WHERE deal_id = <id> ORDER BY id;
SELECT first_response_at, assignee_id FROM deals WHERE id = <id>;
```

У исходящего сообщения есть `external_id` от Telegram; у сделки заполнено время первого ответа (используется в KPI).

**Ограничения:** в историю попадает только реально доставленное сообщение — при ошибке Telegram (бот заблокирован) менеджер видит причину, запись не создается. У заявки с сайта обратного канала нет — система сообщает об этом вместо поля ответа.

## Сценарий 3. Задача на КП дизайнеру → уведомление → макет в карточке сделки

**Требования:** FR-TASK-01–03 · **Автотест:** `test/tasks.test.js` (на обоих вариантах хранилища — диск и БД)

**Исходные условия:** сделка без задач, например новое обращение из сценария 1; демо-сделка «Визитки и буклеты для выставки» показывает уже пройденный сценарий.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | `manager`: «Входящие» → сделка → вкладка «Задачи» → «Поставить задачу»: название, исполнитель `Денис Дизайнер`, срок, ТЗ, вложение | Задача в списке со статусом «Новая» |
| 2 | `designer`: войти | Открывается «Задачи»; в меню счетчик уведомлений, в «Уведомлениях» — «Новая задача: …» |
| 3 | `designer`: открыть задачу, статус «В работе», «Загрузить файл» (PNG/JPG/PDF), статус «На согласовании» | Файл с миниатюрой в задаче |
| 4 | `manager`: вкладка «Задачи» сделки | Видны статус «На согласовании» и миниатюра макета; менеджеру пришли уведомления о файле и статусе |

**Независимая проверка:**

```sql
SELECT t.title, t.status, u.login AS assignee FROM tasks t JOIN users u ON u.id = t.assignee_id WHERE t.deal_id = <id>;
SELECT original_name, mime_type, size_bytes, task_id, deal_id, stored_path FROM files WHERE deal_id = <id>;
SELECT u.login, n.type, n.title, n.is_read FROM notifications n JOIN users u ON u.id = n.user_id ORDER BY n.id DESC LIMIT 5;
```

Метаданные файла привязаны и к задаче, и к сделке; содержимое лежит в хранилище (`docker compose exec backend ls -R /app/storage`).

**Ограничения:** ставить задачи могут только сотрудники отдела продаж; исполнитель меняет статус, но не содержание задачи; посторонний сотрудник не видит ни задачу, ни файл (ответ 404); пустой файл и неподдерживаемые форматы (например, `.html`) отклоняются.

## Сценарий 4. Счет в PDF → отметка оплаты → «Оплачено» и проект

**Требования:** FR-DOC-01, 02, FR-PROJ-01 · **Автотест:** `test/invoices.test.js`

**Исходные условия:** сделка с суммой больше нуля не в «Отказе» и не оплачена. В демо-наборе — «Световая вывеска» (Кофейня «Зерно», счет выставлен) или любая новая сделка.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | `manager`: в сделке указать сумму, вкладка «Счета» → «Сформировать счет» → «Сформировать PDF» | Счет № СЧ-2026-NNNN «Ожидает оплаты»; стадия сделки — «Счет выставлен» |
| 2 | «Открыть PDF» | Счет с реквизитами агентства и клиента, суммой сделки и суммой прописью |
| 3 | «Отметить оплату», подтвердить | Счет «Оплачен»; стадия «Оплачено» (список стадий заблокирован); ссылка на созданный проект |
| 4 | «Проекты» | Проект на этапе «Дизайн» с ответственным менеджером |

**Независимая проверка:**

```sql
SELECT number, amount, status, paid_at FROM invoices WHERE deal_id = <id>;
SELECT stage, closed_at FROM deals WHERE id = <id>;
SELECT p.id, p.status, s.code, s.is_done FROM projects p JOIN project_stages s ON s.project_id = p.id WHERE p.deal_id = <id> ORDER BY s.position;
```

**Ограничения:** счет не формируется при нулевой сумме и для сделки в «Отказе»; стадии «Счет выставлен» и «Оплачено» нельзя поставить вручную в обход счета; повторная отметка оплаты не создает второй проект (уникальность `projects.deal_id`); оплату нельзя откатить, а оплаченную сделку — вернуть на прежнюю стадию. Этапы проекта отмечаются только по порядку.

## Сценарий 5. «Отказ» только после выбора причины; причина в отчете

**Требования:** FR-DEAL-03, FR-AN-03 · **Автотест:** `test/reports.test.js`, `test/leads.test.js`

**Исходные условия:** открытая сделка (например, «Меню-борд и наклейки на витрину»).

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | `manager`: во «Входящих» выбрать стадию «Отказ» | Стадия не меняется; появляется форма с обязательной причиной; кнопка неактивна до выбора причины |
| 2 | Выбрать причину «Дорого», комментарий, «Перевести в «Отказ»» | Стадия «Отказ», под ней причина и комментарий |
| 3 | `head` или `marketer`: «Отчеты» → «Причины отказа» за текущий месяц | Причина учтена в счетчике и доле; сделка — в списке с комментарием |

**Независимая проверка:**

```sql
SELECT d.stage, rr.name, d.refusal_comment, d.closed_at FROM deals d JOIN refusal_reasons rr ON rr.id = d.refusal_reason_id WHERE d.id = <id>;
```

**Ограничения:** запрос `PATCH /api/deals/<id>` со стадией `refused` без причины отклоняется сервером (400) — проверка не только в интерфейсе; дополнительно в БД стоит ограничение `deals_refusal_reason_required`. Скрытая в справочнике причина недоступна для выбора.

## Сценарий 6. Клиент видит текущий этап своего проекта и архив

**Требования:** FR-PORT-01, 02, ТЗ п. 4.7 · **Автотест:** `test/portal.test.js`

**Исходные условия:** у клиента есть проект в работе и завершенный проект; менеджер создал ему учетную запись. В демо-наборе — клиент `client` (Ирина Волкова): проект «Новогодний баннер на щит» на этапе «Печать», в архиве — «Наружная реклама: три щита в центре».

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | (для нового клиента) `manager`: карточка клиента → «Личный кабинет» → логин и пароль → «Создать доступ» | Блок показывает логин и «Доступ открыт» |
| 2 | Войти как `client` | Открывается «Мои заказы»: проект с шкалой этапов и текущим этапом, счета, архив |
| 3 | `manager`/`head`: в проекте отметить этап «Печать» | После обновления страницы у клиента текущий этап — «Размещение» |

**Независимая проверка:**

```sql
SELECT u.login, r.code, u.client_id FROM users u JOIN roles r ON r.id = u.role_id WHERE r.code = 'client';
SELECT id, title, status FROM projects WHERE client_id = <client_id>;
```

**Ограничения:** клиент видит только данные своей карточки — идентификатор берется из учетной записи, а не из запроса: чужой проект или счет по прямой ссылке отвечает 404, рабочие разделы (`/api/inbox`, `/api/projects`, `/api/tasks`…) — 403. Внутренние данные (кто отметил этап, переписка менеджеров) клиенту не передаются. Заблокированная учетная запись перестает работать сразу, даже с действующим токеном.

## Сценарий 7. Руководитель видит KPI менеджеров и отчет по каналам за период

**Требования:** FR-AN-01, 04 · **Автотест:** `test/reports.test.js`, `test/demo.test.js`

**Исходные условия:** в периоде есть обращения из разных каналов и кампаний, назначенные разным менеджерам, часть оплачена (демо-набор).

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | `head`: «Отчеты» → «Каналы и кампании», период «Этот месяц» | Лиды, успешные сделки, конверсия, сумма — итогом, по каналам и по кампаниям; расходы и стоимость лида/клиента |
| 2 | Сменить период на «Прошлый месяц» | Цифры пересчитаны (по демо-набору — нули) |
| 3 | Вкладка «KPI менеджеров» | По каждому менеджеру: лиды, обработано, успешные, отказы, конверсия, сумма, среднее время первого ответа |
| 4 | «Скачать CSV» | Файл открывается в Excel с теми же цифрами |

**Независимая проверка** (сверка с отчетом за текущий месяц):

```sql
SELECT source_channel, count(*) AS leads, count(*) FILTER (WHERE stage = 'paid') AS won,
       sum(amount) FILTER (WHERE stage = 'paid') AS won_amount
  FROM deals WHERE created_at >= date_trunc('month', now()) GROUP BY source_channel;
```

**Ограничения:** KPI и ожидаемая выручка доступны руководителю отдела продаж, директору и администратору; маркетологу — только каналы и отказы; менеджеру и дизайнеру отчеты недоступны (403). Период с началом позже конца отклоняется.
