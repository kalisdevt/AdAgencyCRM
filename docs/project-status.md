## Состояние требований и проектных материалов

ТЗ ред. 2.0 определяет MVP CRM рекламного агентства, обязательные каналы Telegram и веб-форму сайта, желательный канал VK, роли сотрудников/клиента/администратора, функциональные и нефункциональные требования и приемочные сценарии.

- **Объем сокращен до MVP, реализуемого одним разработчиком за семестр.** Исключены: интеграция с Avito (платный доступ к API), автоматическое обогащение карточки клиента данными из соцсетей (ограничения API и 152-ФЗ), интеграция с банком (статус счета меняется вручную), отправка счета по e-mail, интеграция с сервисом отложенного постинга, импорт данных из рекламных кабинетов, двухфакторная аутентификация, импорт из XLSX.
- **Каналы связи:** обязательные — Telegram-бот и веб-форма сайта; ВКонтакте — желательный. Модуль каналов строится на адаптерах, чтобы исключенные каналы можно было добавить позже.
- **Устранены противоречия между материалами:** UC-7 в диаграмме ВИ назывался «Создание и отправка отчета», в ЛР № 1 и ТЗ — «счета» (принят «счет»); актор «SMM-специалист» из ЛР № 2 и компонент Posting Service из ЛР № 4 убраны вместе с функцией отложенного постинга; наименование объекта унифицировано («рекламное агентство»).
- **Требования формализованы:** присвоены идентификаторы (FR-…), приоритеты (обязательное/желательное) и трассировка к ПИ и ВИ; добавлены роль «Администратор» и раздел «Характеристика объекта автоматизации».
- **Непроверяемые требования заменены проверяемыми** (вместо «RTO 4 часа» и «современные стандарты UI/UX» — защита от дубликатов сообщений, скрипт резервного копирования, диапазон ширины экрана и т. п.); добавлены приемочные сценарии.
- **Этапы, приемка и документация приведены к формату семестрового проекта:** сроки сентябрь – декабрь 2026, приемка — демонстрация по сценариям, исключены внедрение на сервере Заказчика, миграция данных и обучение персонала.

## Что еще не реализовано

- схема базы данных (перечень сущностей определен в п. 4.3 ТЗ, ER-диаграмма отсутствует);
- макеты интерфейса (экраны «Входящие», карточка клиента, воронка, личный кабинет клиента);
- выбор языка и фреймворков серверной и клиентской части;
- программная реализация: исходный код отсутствует полностью;
- README, описание API, руководство пользователя.

## Необходимые правки в проектных материалах

- **Диаграмма ВИ (ЛР № 2):** переименовать UC-7 в «Создание и отправка счета»; удалить UC-10 и актора «SMM-специалист»; во «Внешних каналах» заменить «Avito, VK, TG» на «Telegram, сайт, VK».
- **Диаграмма компонентов (ЛР № 4):** удалить Avito API и Posting Service; добавить компонент веб-формы сайта.

Лабораторная работа по актуализации UML выполнена на основе ТЗ и материалов ЛР № 2 и № 4. Use-case разделена на функциональные схемы с отдельными PNG-превью и PlantUML-исходниками; сводное изображение — [`uml-use-cases-all.png`](uml-use-cases-all.png), декомпозиция задач — в [`ЛР2_актуализация_UML_декомпозиция.md`](ЛР2_актуализация_UML_декомпозиция.md). Компонентная и последовательностная диаграммы находятся в [`uml-components.puml`](uml-components.puml) и [`uml-sequence-lead.puml`](uml-sequence-lead.puml). Старые отчеты ЛР № 2 и № 4 сохранены как исходные материалы.

Ключевые исправления UML: use-case разделена на небольшие схемы, связи актор–вариант использования показаны ассоциациями без наконечников стрелок; из модели удалены SMM-специалист и UC-10; UC-7 называется «Создание и отправка счета»; Avito и Posting Service удалены из компонентной схемы; добавлена веб-форма сайта, уточнены адаптеры и модули по архитектуре ТЗ. Последовательность приема лида уточнена для Telegram и сайта с проверкой дубликата.

## Реализация

В репозитории присутствует клиент Vue 3/Vite с демонстрационным экраном входа. Отправка формы показывает заглушку о будущем подключении сервера; реальная аутентификация, REST API, база данных и бизнес-сценарии пока отсутствуют. Серверный стек еще предстоит выбрать. Поэтому первый сквозной сценарий (обращение → клиент/лид → лента «Входящие») не реализован.

## Ближайшая работа

Очередность реализации с зависимостями и критериями готовности приведена в документе лабораторной. Начальные задачи: выбрать серверный стек и описать контракты модулей; подготовить каркас API с PostgreSQL через Docker Compose; разработать схему данных. Затем реализовать Telegram и веб-форму, обработку дубликатов, поиск/создание клиента и лида и вывести новые обращения в «Входящие».
