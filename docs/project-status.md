Дата фиксации: 17.11.2026 (этап «Основная функциональность», недели 6–10)  
Разработчик: Тынков Дмитрий  
Актуальное ТЗ: `Техническое_задание_ред_2.0.docx` (редакция 2.0 от 22.09.2026)

## Состояние требований и проектных материалов

ТЗ ред. 2.0 определяет MVP CRM рекламного агентства, обязательные каналы Telegram и веб-форму сайта, желательный канал VK, роли сотрудников/клиента/администратора, функциональные и нефункциональные требования и приемочные сценарии.

- **Объем сокращен до MVP, реализуемого одним разработчиком за семестр.** Исключены: интеграция с Avito (платный доступ к API), автоматическое обогащение карточки клиента данными из соцсетей (ограничения API и 152-ФЗ), интеграция с банком (статус счета меняется вручную), отправка счета по e-mail, интеграция с сервисом отложенного постинга, импорт данных из рекламных кабинетов, двухфакторная аутентификация, импорт из XLSX.
- **Каналы связи:** обязательные — Telegram-бот и веб-форма сайта; ВКонтакте — желательный. Модуль каналов строится на адаптерах, чтобы исключенные каналы можно было добавить позже.
- **Устранены противоречия между материалами:** UC-7 в диаграмме ВИ назывался «Создание и отправка отчета», в ЛР № 1 и ТЗ — «счета» (принят «счет»); актор «SMM-специалист» из ЛР № 2 и компонент Posting Service из ЛР № 4 убраны вместе с функцией отложенного постинга; наименование объекта унифицировано («рекламное агентство»).
- **Требования формализованы:** присвоены идентификаторы (FR-…), приоритеты (обязательное/желательное) и трассировка к ПИ и ВИ; добавлены роль «Администратор» и раздел «Характеристика объекта автоматизации».
- **Непроверяемые требования заменены проверяемыми** (вместо «RTO 4 часа» и «современные стандарты UI/UX» — защита от дубликатов сообщений, скрипт резервного копирования, диапазон ширины экрана и т. п.); добавлены приемочные сценарии.
- **Этапы, приемка и документация приведены к формату семестрового проекта:** сроки сентябрь – декабрь 2026, приемка — демонстрация по сценариям, исключены внедрение на сервере Заказчика, миграция данных и обучение персонала.

## Реализация

### Этап «Базовая реализация» (недели 3–5)

Система запускается одной командой `docker compose up --build` и проходит первый сквозной сценарий — обращение из Telegram или с веб-формы → поиск/создание клиента и лида → лента «Входящие» → работа менеджера с обращением. Серверный стек — Node.js 24, Express 5, PostgreSQL 17 без ORM (SQL-миграции), zod, JWT и bcrypt; клиент — Vue 3, Vite, vue-router. Лид — сделка на стадии «Новый»; идемпотентность приема — уникальное ограничение на пару «канал + ID сообщения»; лента обновляется опросом раз в 5 секунд.

### Этап «Основная функциональность» (недели 6–10)

Система решает основную задачу ТЗ целиком: реализованы **все 24 обязательных требования** раздела 4.2 и 5 из 7 желательных; **все семь приемочных сценариев п. 6.2** проходят в запущенном приложении и закреплены автотестами. Перечень требований — [`requirements-status.md`](requirements-status.md), проверка сценариев по критериям (исходные условия, шаги, независимая проверка по БД, ограничения, воспроизводимость) — [`acceptance-scenarios.md`](acceptance-scenarios.md), руководство по ролям — [`user-guide.md`](user-guide.md).

**Принятые решения этапа.**

- **Файловое хранилище** с единым интерфейсом (`backend/src/storage.js`): локально и в Docker — каталог на диске (том `files`), на Vercel — таблица `file_contents` в PostgreSQL, потому что диск контейнера там не сохраняется. Метаданные всегда в таблице `files` (ТЗ п. 4.3). Тип файла определяется сервером по расширению из белого списка, файлы отдаются с `nosniff` и CSP.
- **Стадии «Счет выставлен» и «Оплачено» связаны со счетами**: первая ставится при формировании счета, вторая — при отметке оплаты, вручную в обход счета их поставить нельзя; оплаченную сделку нельзя вернуть на прежнюю стадию. Так отчеты и проекты не расходятся со счетами.
- **Проект создается в одной транзакции с отметкой оплаты**; повторная отметка не создает второй проект (уникальность `projects.deal_id`). Этапы отмечаются строго по порядку.
- **PDF** — библиотека `pdfkit` со встроенным шрифтом DejaVu Sans (кириллица); реквизиты агентства задаются переменными окружения, по умолчанию — заведомо тестовые.
- **Отчеты считаются когортно**: лиды периода — сделки, созданные в эти даты; успешные — те из них, что оплачены. Отказы — по дате перевода в «Отказ». Даты — в часовом поясе агентства (`REPORT_TIMEZONE`).
- **Кабинет клиента** берет идентификатор клиента только из учетной записи; клиенту не передаются внутренние данные (переписка, кто отметил этап).
- **Резервная копия** теперь включает и файловое хранилище.

**Ограничения текущего состояния.** Ответ клиенту, отправка счета и уведомления о смене этапа работают только для Telegram и только при заданном токене бота; без токена система честно сообщает, что канал не подключен. Лента и счетчик уведомлений обновляются опросом (5 и 20 секунд) — этого достаточно для требования «в течение 10 секунд».

### Работа с репозиторием

Изменения этапа разбиты на пять веток и pull request с небольшими проверенными коммитами: задачи и уведомления → счета и проекты → кабинет клиента → отчеты и справочники → демо-данные и документация. Каждый PR основан на предыдущем и после слияния предыдущих переключается на `master`.
